# SGEMM 优化总结(V0 → V9)

> 项目:`E:/AI_Infra/CUDA/Sgemm/kernel.cu`
> 硬件:NVIDIA GeForce RTX 5070 Ti(compute capability 12.0 / sm_120)
> 矩阵:4096 × 4096 × 4096,FP32
> 结论:CUDA Core 路线从 **2590 GFLOP/s 优化到 ~28 TFLOPS(约 60% 峰值)**,10.7 倍提升;再往上需换 Tensor Core。

---

## 1. 环境与目标

| 项目 | 值 |
|---|---|
| GPU | RTX 5070 Ti(sm_120,Blackwell) |
| FP32 峰值 | ~46 TFLOPS(CUDA Core) |
| 矩阵尺寸 | M = N = K = 4096 |
| 最终成绩 | ~28 TFLOPS ≈ **60% 峰值** |
| 工具链 | VS 2026 + CUDA 13.5 + cuBLAS(参考基准) |

> ⚠️ 实测注意:5070 Ti 的 boost 频率受温度影响漂移明显,不同次运行绝对 GFLOP/s 有 ±10% 波动。**所有对比必须看同一次运行内的相对值**。

## 2. 优化历程总览

| 版本 | 核心技巧 | 解决的瓶颈 | GFLOP/s(代表值) | 加速比 |
|---|---|---|---|---|
| V0 | 朴素:每线程算一个输出点,直接读全局内存 | 正确性基线 | ~2600 | 1.0x |
| V2 | 共享内存 K 方向分块(tiling) | 全局内存重复读 | ~4100 | 1.6x |
| V3 | 每线程算多个输出点 | 线程并行度浪费 | ~4100 | 1.6x |
| V4 | 多 tile + 寄存器累加 | 共享内存反复读 | ~15700 | 6.0x |
| V5_0 | 寄存器分块 TM×TN(标量、不转置) | V4 的 smem 带宽瓶颈 | ~19200 | 7.3x |
| **V5** | **A 转置 + float4 向量化** | A 跨步读的 bank conflict | ~27000 | 9.9x |
| **V7** | **双缓冲(寄存器预取)** | 加载/计算串行 | **~28000** | **10.5x** 🏆 |
| V8 | cp.async 异步拷贝 | 同上(但被迫非转置) | ~26000 | 8~9x |
| V9 | cp.async + K 方向 float4 读 | V8 的 A 读退化 | ~26000 | 8~9x |

**BK 调参(V5 扫 8/16/32)**:非单调!BK=16 反而最慢(~21800),BK=8 和 BK=32 打平。

## 3. 各版本详解

### V0 — 朴素实现
每个线程负责 C 的一个元素,从全局内存读 A 的一行、B 的一列做点积。
**问题**:每个 A 元素被 N 个线程重复读、每个 B 元素被 M 个线程重复读,全局带宽爆炸。

### V2 — 共享内存分块
把 K 切成小块,先协作搬进共享内存,再从 smem 读。**关键思想:全局内存读一次,smem 读多次复用。**

### V4 — 多 tile + 寄存器累加
每个线程算 perRowNum×perColNum 个输出点,累加器放寄存器。
**问题(注释里明确写的)**:每次乘加都要从 smem 读两次 → smem 带宽瓶颈,且存在重复读。

### V5_0 — 寄存器分块(在 V4 基础上"进一步 tiling")
把循环顺序从 `for r,c,s`(内积式,每点扫 K)改成 `for k: 装寄存器 → 8×8 外积`(外积式)。
**核心收益**:`a[8]` 复用于 8 个 n、`b[8]` 复用于 8 个 m → **读 16 次换 64 个 FMA**。
这一版刻意**不用 float4、不转置**,纯粹量化"寄存器复用"的贡献:**+21%**(相对 V4)。

### V5 — A 转置 + float4 向量化
- **A 转置存** `As[BK][BM]`:计算需要 A 的"一列"(固定 k、8 个连续行),行主序里跨行不连续;转置后变成 As 的一行 → **连续、float4 读、零 bank conflict**
- **B 不转置**:B 需要的"一行"(固定 k、8 个连续列)行主序天然连续
- float4 全局加载 + 转置 scatter 写入 smem(写有 2-way 冲突,但低频,值得换高频读的零冲突)

### V7 — 双缓冲(double buffering)🏆 最终赢家
两块 smem 交替:算当前块时,预取下一块到寄存器(load 非阻塞,延迟被 8×8 外积计算隐藏),计算后写进另一块 smem。
- 同步从每轮 2 次降到 1 次
- 全局加载延迟被计算覆盖
- 寄存器预取只占 1+1 个 float4(BK=8 时),代价极小

### V8 — cp.async 异步拷贝
`cp.async.cg` 全局→smem 直接搬,不占寄存器、发完即返回,配合 commit_group/wait_group。
**代价**:cp.async 只能 16B 连续拷贝、**无法转置** → A 必须非转置 → A 读退回跨步标量读,丢了 V5 最值钱的转置优化。

### V9 — cp.async + K 方向 float4 读
修复 V8 的 A 读退化:沿 K 读 float4。但寄存器占用翻倍(a[8][4]+b[4][8]=64 额外寄存器)→ occupancy 下降,且 BK=8 下沿 K 的 float4 读仍有 2-way conflict。

## 4. 性能曲线与结论

```
GFLOP/s
28000 ┤                                    ●V7  ← CUDA Core 终点
26000 ┤                          ●V5
24000 ┤
20000 ┤                 ●V5_0
16000 ┤          ●V4
12000 ┤
 8000 ┤
 4000 ┤   ●V2/V3
      └──┴──┴──┴──┴──┴──┴──┴──┴──┴──→ 版本
      V0 V2 V3 V4 V5_0 V5 V7 ...

峰值 46 TFLOPS,最终 28 TFLOPS ≈ 60%。剩下 40% 是 FP32 CUDA Core 的物理墙。
```

**结论**:
1. **CUDA Core 路线的最佳答案 = V7**(转置 A + float4 + 寄存器预取双缓冲)
2. **cp.async 路线(V8/V9)在纯 FP32 下是死路**——它逼 A 非转置、丢掉转置收益,而它的异步收益又因"加载不是瓶颈"而落空
3. **BK 调参非单调**——BK=16 是"坏点",只能实测
4. 要突破 60% 峰值,只有 **Tensor Core**(TF32 是 FP32 的 3~4 倍吞吐)

## 5. 核心概念清单

| 概念 | 一句话 |
|---|---|
| 内存合并访存 | warp 的 32 个地址按 **32B sector** 分桶合并,利用率按 sector 内有用字节算 |
| 共享内存 tiling | 全局读一次、smem 复用多次 |
| bank conflict | 32 banks × 4B,同 bank 多地址才冲突;转置/padding 可消除 |
| 寄存器分块 | 操作数装寄存器,一次加载复用 TM×TN 次 |
| 内积 vs 外积 | 内积=行·列→标量(每点扫 K);外积=列·行→矩阵(每 k 更新整块) |
| float4 向量化 | 128-bit 访存,指令数 ÷4,2 线程填满 1 个 sector |
| 转置存储 | 让热循环的读取方向对齐到连续内存 |
| 双缓冲 | 两块 smem 交替,加载与计算重叠 |
| cp.async | 异步拷贝,不占寄存器,需 ldmatrix 才能配转置 |
| occupancy | 寄存器/共享内存/线程数 三者互相挤占,是调参的三角权衡 |

## 6. 关键教训(踩过的坑)

1. **优化不能无脑叠加**:每个技巧有适用条件。cp.async 单打独斗 = 净亏损,必须配 ldmatrix + Tensor Core。
2. **寄存器预取式双缓冲不适用于大 BK**:BK=32 时预取要 4+4 个 float4(32 寄存器),寄存器压力爆炸。大 BK 的双缓冲该用 cp.async。
3. **48KB 静态 smem 上限**:V7 双缓冲 BK=32 需 64KB,必须 `extern __shared__` + `cudaFuncSetAttribute` opt-in。
4. **动态 smem + 运行时指针**会让编译器丢掉 float4 向量化(无法证明 16B 对齐)——用 `float4*` 类型指针保住对齐信息。
5. **双缓冲的经典竞态**:cp.async 在迭代开头写下一块,必须计算后再 `__syncthreads`(每轮 2 个 sync,和 CUTLASS 一致),否则快线程会覆盖慢线程还在读的块。
6. **每线程 float4 数 = BM×BK/4/线程数**:只有 BK=8 时才是 1;BK 变大必须加加载循环,否则 tile 只搬了 1/4(结果错误)。
7. **测量噪声**:boost 频率波动 ±10%,对比必须同一次运行内做,最好多次取中位数。

## 7. 下一步:Tensor Core 路线

```
① WMMA API(nvcuda::wmma)      ← 入门,易上手
② mma.sync PTX 指令            ← 进阶,手动控制 fragment
③ ldmatrix                     ← smem→寄存器硬件转置(cp.async 的补完)
④ TMA(cp.async.bulk.tensor)   ← Blackwell 硬件批量拷贝
⑤ thread block cluster         ← 集群共享 smem
```

目标:TF32 精度下 **80~150+ TFLOPS**(数倍于 FP32 CUDA Core 峰值)。cuBLAS/CUTLASS 的本质 = 本项目的全部技巧 + Tensor Core + ldmatrix + TMA 的组合。
