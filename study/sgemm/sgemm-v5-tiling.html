SGEMM V5 分块策略详解

cudaSgemm_V5：每个 block 算 128×128 输出块 · 每个线程算 8×8 微块 · K 方向按 BK=8 条带循环 · float4 向量化
M=N=K=4096矩阵尺寸
BM=BN=128每个 block 的输出 tile
BK=8K 方向条带宽度
16×16=256每 block 线程数
TM=TN=8每线程微块 8×8
32×32=1024grid 中 block 数
512 次K 循环迭代数

① 第一层分块：C 被切成 32×32 个 block

把输出 C(4096×4096)按 BM×BN = 128×128 切成 32×32 = 1024 个块（4096 ÷ 128 = 32），每个 GPU block 独立计算一个 tile。

以 block(4, 7) 为例：C(4×128, 7×128) = C(512, 896)，负责 C 的 512~640 行 × 896~1024 列。它只需要两份输入：A 的第 4 行块（512~640 行 × 全部 K 列）和 B 的第 7 列块（全部 K 行 × 896~1024 列）。

A 第 4 行块（rows 512~640 × 全部 K 列） B 第 7 列块（全部 K 行 × cols 896~1024） block(4,7) 的 128×128 输出 tile 虚线 = 行列对齐

② 第二层分块：K 方向按 BK=8 切条带

一个 block 要的输入太大（128 行 × 全部 4096 列），共享内存放不下。于是把 K 切成 K/BK = 512 个条带，每次迭代只搬一对 8 宽的条带进共享内存。

注意两条带的形状和摆放方向不同：A 条带是竖条（128 行 × 8 列，竖着的 128 是 M 行方向），512 个竖条沿 K 横向排开；B 条带是横条（8 行 × 128 列，横着的 128 是 N 列方向），512 个横条沿 K 纵向堆叠——因为 K 在 A 里是列号、在 B 里是行号。

for (kb = 0; kb < 4096; kb += 8) { // 512 次迭代 加载 A 竖条(128×8) → As；加载 B 横条(8×128) → Bs 128×128 tile 累加 += 条带外积 }
当前第 256 个条带 A：竖条（128 行 × 8 列） B：横条（8 行 × 128 列） 其余条带

③ 块内分工：16×16 线程，每人一个 8×8 微块

block 内有 16×16=256 个线程，128×128 的 tile 再切成 8×8 的微块，每个线程负责一块：

threadRow = ty * 8 // 线程微块的行起点（0,8,...,120） threadCol = tx * 8 // 线程微块的列起点（0,8,...,120） // 该线程累加 acc[8][8]，最终写回 C[threadRow..+8][threadCol..+8]
线程 (ty=3, tx=9) 的 8×8 微块 它需要读的 A 片段（8 行 × 固定 k） 它需要读的 B 片段（固定 k × 8 列）

④ 线程搬运分工：256 个 float4 怎么分

一个 A 条带（128×8）和一个 B 条带（8×128）都是 1024 个 float = 256 个 float4，block 里正好 256 个线程，所以每个线程每轮只搬 1 个 float4，一轮正好搬完。线程线性编号 i = ty×16 + tx（tx 变化最快）：

A 条带：每行 8 列 = 2 个 float4 → row = i / 2，col = (i % 2) × 4。线程 0、1 搬第 0 行，2、3 搬第 1 行……254、255 搬第 127 行（从上到下、从左到右）。

B 条带：每行 128 列 = 32 个 float4 → row = i / 32，col = (i % 32) × 4。线程 0~31 搬第 0 行，32~63 搬第 1 行……224~255 搬第 7 行。

循环写成 for (i = 线程号; i < 256; i += 256) 是为了通用性：若 BK=16，条带有 512 个 float4，每个线程自动搬 2 轮。

A 条带（128 行 × 8 列 = 256 float4） B 条带（8 行 × 128 列 = 256 float4） 1 个 float4 = 4 个连续 float = 16 字节

⑤ 计算部分：寄存器微块 + 逐 k 外积

搬运完条带后，两个条带做乘法就得到 128×128 的累加。V5 与 V4 的区别不在"分割输出"，而在循环顺序：先把 A/B 各 8 个操作数装进寄存器，再做 8×8 外积，让一次加载被 8 次 FMA 复用。

每个线程 (ty, tx) 负责输出微块 C[threadRow..+8][threadCol..+8]。对条带内每个 k（0..7），它读 A 的 As[k][threadRow..+7]（8 个值）和 B 的 Bs[k][threadCol..+7]（8 个值），做一次 rank-1 外积累加：

for (k = 0; k < 8; ++k) { a[8] = As[k][threadRow..+7]; b[8] = Bs[k][threadCol..+7]; // 16 次读（4×float4） for (m) for (n) acc[m][n] += a[m] * b[n]; // 64 个 FMA }
线程(ty=3) 的 A 片 As[k][24..32)（8 个值） 线程(tx=9) 的 B 片 Bs[k][72..80)（8 个值） acc[8][8]（64 个寄存器累加器） 当前第 k 行

补充：内积 vs 外积（为什么这样算）

矩阵乘法有两种等价写法，V4 用内积、V5 用外积，循环顺序相反、结果相同：

内积（行·列 → 标量）：外层 (i,j)、内层 k，一次算 1 个输出元素。外积（列·行 → 矩阵）：外层 k、内层 (i,j)，一次 k 更新整个输出块。

A（2×3） B（3×2） C（2×2） 本次参与计算的行/列/元素

V4 vs V5：循环顺序决定复用率

V4（registerSum）V5（register tiling）
循环结构for r → c → s，每个输出点扫一遍 Kfor k → 装寄存器 → 8×8 外积
smem 读 / FMA2 读 : 1 FMA16 读 : 64 FMA = 1 : 4
操作数复用无（重复读）每个值复用 8 次
瓶颈共享内存带宽寄存器 / FMA 算力

⑥ 共享内存布局：A 转置存，B 直存

As[BK][BM] = As[8][128]（A 转置）

k 作行、m 作列。线程读 As[k][threadRow..+7] 时 8 个元素地址连续 → 2 次 float4 读、无 bank conflict。

Bs[BK][BN] = Bs[8][128]（B 直存）

k 作行、n 作列。B 行主序天然 n 连续，Bs[k][threadCol..+7] 同样是 2 次 float4、无冲突，所以 B 不需要转置。

为什么转 A 不转 B：热循环固定 k 时，A 需要"沿 M 方向连续"（行主序里跨行不连续 → 必须转置），B 需要"沿 N 方向连续"（行主序里同行内天然连续 → 不用转）。

⑦ 一次 K 迭代的完整数据流（可单步播放）

A 条带（全局内存） B 条带（全局内存） 共享内存 As / Bs 当前阶段

项目V4（多 tile + 寄存器累加）V5（register tiling + float4）
共享内存perRowNum×perColNum 个 16×16 tileAs 4KB + Bs 4KB = 8KB
每 FMA 的 smem 读2 次标量读（带宽瓶颈）2/64 次（16 次读换 64 个 FMA）
smem 读指令标量 LDS × Nfloat4 LDS（128-bit）
bank conflict存在反复读取A 转置 + float4 → 0 冲突
每线程寄存器perRowNum×perColNum 个累加器64 累加器 + a[8] + b[8] ≈ 80
写回全局每 tile 一次每 tile 一次（整个 K 循环结束）
V5 把"读共享内存"这个热路径操作量降到 V4 的 1/8，并用 float4 把指令数再 ÷4；转置 A 把冲突清零。代价是加载时 A 的 scatter 写有少量冲突，但写每 tile 只发生一次，读却发生在 8×8 外积的每一次——低频写冲突换高频读零冲突，稳赚。

⑨ 下一步（V6 方向）

  • BK=8 太小：每 8 列就要一次 __syncthreads，流水线切太碎；经典配置 BK=16/32
  • 双缓冲 + cp.async：让第 kb+1 条带的加载与第 kb 条带的计算重叠，消除同步等待
  • ldmatrix：用 Tensor Core 时代的方式把 smem → 寄存器转置加载，替代手写转置
  • L2 级分块：让相邻 block 复用 A 的同一行块，减少全局带宽压力
